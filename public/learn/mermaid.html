What it is, and why they care

You type something like A --> B and Mermaid draws a box A with an arrow to box B. That's the whole idea. The text lives in a Markdown file next to the code, so it gets saved in Git, reviewed in pull requests, and updated like any other file. That's what diagram-as-code and docs-as-code mean.

GitHub, GitLab, Azure DevOps wikis, Notion, and Obsidian all draw Mermaid automatically inside Markdown. Confluence needs a plugin.

Why a modernization team cares:

  • Diagrams stop going stale. A Visio file on someone's laptop is out of date in a month. A Mermaid file in the repo gets updated in the same pull request as the change.
  • You can see what changed. Git shows exactly which arrow moved and who moved it.
  • AI writes it well. You can paste messy notes into Claude and get a working first draft in seconds. That's the "AI-assisted documentation" line in the job description.

Cheat sheet

You typeYou get
flowchart LR / TDStart a flowchart. LR runs left to right, TD runs top down.
A[Text]Rectangle (a step or system)
A(Text)Rounded box (start or end)
A{Text}Diamond (a decision)
A[(Text)]Cylinder (a database)
A --> BSolid arrow
A -.-> BDotted arrow (optional, async, or "going away")
A -->|label| BArrow with words on it
subgraph Name ... endA labeled box around a group (a team, a system, a state)
A{Approved?} -->|Yes| BBranch out of a decision
%% noteA comment that doesn't show up
A->>B: msgSequence diagram: call. -->> is the response.

Most common mistake: a label with parentheses or special characters inside [ ] breaks it. Wrap the label in quotes, like A["Pricing (legacy)"].

How it'll show up in the interview

They listed what they want you to demonstrate: a PRD, a modernization plan, dependency mapping, technical writing, architecture docs, a Mermaid diagram, migration and risk planning, and using AI to help. Expect a scenario like "we have an old system, walk us through how you'd replace it." Here's the order to answer in:

  1. Ask questions first. Who uses it? What depends on it? What can't go down?
  2. Draw the current state (diagram 1 or 2). Say the risks out loud as you draw.
  3. Draw the future state next to it.
  4. Plan the move in phases (diagram 4): discover, build, run both side by side, cut over, retire the old one.
  5. Name the risks and what you'd do about each: data migration, downtime, people who aren't trained yet, and things nobody knew depended on the old system.
Stay honest about your level. Mermaid is on your resume now, so get real reps in before next week so it's true when you say it. If they ask how long you've used it, a good answer is that you've used diagramming tools for years (SharePoint, Smartsheet, process maps at Tampa Electric and MITER) and moved to Mermaid because it keeps docs next to the code. Then show them.
If they ask why Mermaid"Because the diagram lives in the repo with the code. When the system changes, the diagram changes in the same pull request, so it doesn't go stale like a Visio file."
If they ask how you use AI"I'll paste my discovery notes into Claude and have it draft the Mermaid. Then I check every box and arrow against what the engineers told me. AI gets me a first draft fast, and I make sure it's right."
If they ask about legacy risk"The scariest dependencies are the ones nobody wrote down. So I map what we know first, then confirm it with the people who run it every day before we touch anything."

The rest of their tool list, in plain English

TermWhat it is
EncompassA loan origination system (LOS) from ICE Mortgage Technology. It's where mortgage loans get created, processed, and closed. It's a big deal in mortgage.
SalesforceA CRM. In mortgage it usually tracks leads, brokers, and borrower relationships.
Microsoft AzureMicrosoft's cloud, where apps, databases, and APIs run.
Microsoft FabricMicrosoft's data and analytics platform. It brings data together for reporting, with Power BI built in.
PlantUMLAn older, similar tool. Text in, diagram out. Its syntax is wordier than Mermaid's.
C4 modelA way to draw architecture at four zoom levels: Context (the system and its users), Containers (apps and databases), Components (the pieces inside one app), and Code. Usually you only draw the first two.
Lucidchart, Visio, MiroDrag-and-drop diagram tools. Good for workshops and whiteboarding, but they don't live with the code.
Event-driven architectureSystems announce things ("loan funded") and other systems react, instead of calling each other directly.
Technical debtShortcuts and old code that make every future change slower and riskier.
